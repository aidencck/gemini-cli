# 代码架构重构Prompt模板

## 概述
本模板用于对现有代码进行架构重构分析，提供系统性的改进方案，提高代码质量、可维护性和性能。

## 使用场景
- 代码质量改进
- 系统性能优化
- 技术债务清理
- 架构模式升级
- 代码可维护性提升

## Prompt模板

```
# 代码架构重构Prompt

请对以下代码进行架构重构分析，提供改进方案：

## 重构目标
- 提高代码可维护性和可读性
- 优化性能和资源使用
- 增强扩展性和灵活性
- 改善错误处理和安全性

## 分析维度

### 1. 代码结构分析
- 分析文件组织和模块划分
- 评估代码耦合度和内聚性
- 识别重复代码和设计模式

### 2. 架构模式评估
- 评估当前使用的架构模式
- 识别模式应用的最佳实践
- 建议更合适的架构模式

### 3. 性能优化分析
- 识别性能瓶颈和优化机会
- 分析内存使用和资源管理
- 评估并发处理和异步操作

### 4. 安全性和错误处理
- 分析安全漏洞和风险点
- 评估错误处理机制
- 建议安全加固措施

### 5. 可测试性分析
- 评估代码的可测试性
- 识别测试覆盖不足的区域
- 建议测试策略改进

## 输出要求

请提供：
1. 当前架构问题分析
2. 重构后的架构设计
3. 重构步骤和迁移计划
4. 代码示例和最佳实践
5. 测试策略和验证方案
6. 风险评估和回滚计划

## 代码内容
[在此处粘贴需要重构的代码]
```

## 分析维度详解

### 1. 代码结构分析
**目标**: 理解当前代码的组织结构和模块划分
**关注点**:
- **文件组织**: 文件命名、目录结构、模块划分
- **依赖关系**: 模块间的依赖关系和循环依赖
- **代码重复**: 重复代码、相似逻辑、工具函数
- **设计模式**: 当前使用的设计模式和适用性

**重构方向**:
- 重新组织文件结构，提高模块化程度
- 消除循环依赖，建立清晰的依赖层次
- 提取公共代码，减少重复
- 应用合适的设计模式

### 2. 架构模式评估
**目标**: 评估当前架构模式的适用性和改进空间
**关注点**:
- **当前模式**: MVC、MVVM、分层架构等
- **模式匹配**: 模式与业务需求的匹配度
- **扩展性**: 模式对功能扩展的支持
- **维护性**: 模式对代码维护的影响

**重构方向**:
- 选择更适合的架构模式
- 优化模式的应用方式
- 引入新的架构模式解决特定问题
- 建立架构模式的指导原则

### 3. 性能优化分析
**目标**: 识别和解决性能瓶颈
**关注点**:
- **算法复杂度**: 时间复杂度和空间复杂度
- **资源使用**: 内存、CPU、网络资源使用
- **并发处理**: 异步操作、线程安全、锁机制
- **缓存策略**: 缓存使用和失效策略

**重构方向**:
- 优化算法和数据结构
- 改进资源管理和垃圾回收
- 引入异步处理和并发控制
- 实施多级缓存策略

### 4. 安全性和错误处理
**目标**: 提高代码的安全性和健壮性
**关注点**:
- **输入验证**: 参数验证、边界检查、类型安全
- **错误处理**: 异常捕获、错误恢复、日志记录
- **安全漏洞**: SQL注入、XSS、CSRF等
- **权限控制**: 访问控制、认证授权

**重构方向**:
- 加强输入验证和参数检查
- 完善错误处理和异常管理
- 修复安全漏洞和风险点
- 实施安全最佳实践

### 5. 可测试性分析
**目标**: 提高代码的可测试性和测试覆盖率
**关注点**:
- **依赖注入**: 外部依赖的解耦和注入
- **单一职责**: 函数的单一职责和可测试性
- **测试覆盖**: 单元测试、集成测试覆盖率
- **测试工具**: 测试框架和工具的使用

**重构方向**:
- 引入依赖注入和接口抽象
- 重构函数提高单一职责
- 增加测试用例和覆盖率
- 优化测试策略和工具

## 重构策略

### 1. 渐进式重构
**策略**: 分步骤、小批量进行重构
**优势**:
- 降低重构风险
- 便于验证和回滚
- 减少对业务的影响
- 便于团队学习和适应

**实施步骤**:
1. 识别重构优先级
2. 制定重构计划
3. 逐步实施重构
4. 验证重构效果
5. 持续优化改进

### 2. 模式驱动重构
**策略**: 基于设计模式进行重构
**常用模式**:
- **工厂模式**: 对象创建的统一管理
- **策略模式**: 算法的动态选择
- **观察者模式**: 事件驱动的松耦合
- **装饰器模式**: 功能的动态扩展

**实施步骤**:
1. 识别适用的设计模式
2. 设计模式应用方案
3. 重构代码应用模式
4. 验证模式效果

### 3. 性能驱动重构
**策略**: 基于性能指标进行重构
**性能指标**:
- 响应时间
- 吞吐量
- 资源使用率
- 并发能力

**实施步骤**:
1. 建立性能基准
2. 识别性能瓶颈
3. 设计优化方案
4. 实施性能优化
5. 验证性能提升

## 重构工具和方法

### 1. 代码分析工具
- **静态分析**: ESLint、SonarQube、CodeClimate
- **依赖分析**: Dependency Cruiser、Madge
- **复杂度分析**: Cyclomatic Complexity、Halstead Metrics
- **重复检测**: Jscpd、PMD CPD

### 2. 重构技术
- **提取方法**: 将重复代码提取为独立方法
- **提取类**: 将相关功能提取为独立类
- **移动方法**: 将方法移动到合适的类
- **重命名**: 改进命名提高可读性
- **参数化**: 将硬编码值参数化

### 3. 测试策略
- **单元测试**: 测试重构后的单元功能
- **集成测试**: 测试模块间的集成
- **回归测试**: 确保重构不破坏现有功能
- **性能测试**: 验证性能优化效果

## 风险评估和应对

### 1. 技术风险
- **功能破坏**: 重构可能破坏现有功能
- **性能下降**: 重构可能影响系统性能
- **兼容性问题**: 重构可能影响系统兼容性

### 2. 业务风险
- **开发延期**: 重构可能延长开发周期
- **资源消耗**: 重构需要额外的开发资源
- **学习成本**: 团队需要学习新的架构模式

### 3. 应对策略
- **充分测试**: 建立完善的测试体系
- **渐进实施**: 分步骤进行重构
- **回滚机制**: 建立快速回滚机制
- **团队培训**: 提供必要的技术培训

## 最佳实践

### 1. 重构原则
- **保持功能不变**: 重构不应改变系统功能
- **小步快跑**: 每次重构的改动要小
- **持续测试**: 重构过程中持续进行测试
- **及时反馈**: 及时获取重构效果的反馈

### 2. 代码质量
- **可读性**: 代码应该易于理解和维护
- **可测试性**: 代码应该易于测试
- **可扩展性**: 代码应该易于扩展
- **可维护性**: 代码应该易于维护

### 3. 团队协作
- **代码审查**: 建立代码审查机制
- **知识分享**: 定期进行技术分享
- **文档更新**: 及时更新技术文档
- **经验总结**: 总结重构经验和教训

## 使用技巧

1. **优先级排序**: 根据影响范围和收益确定重构优先级

2. **渐进实施**: 采用渐进式重构，降低风险

3. **充分测试**: 建立完善的测试体系，确保重构质量

4. **团队协作**: 与团队充分沟通，确保重构方案可行

5. **持续改进**: 将重构作为持续改进的过程

## 常见问题

### Q: 如何确定重构的时机？
A: 重构时机判断标准：
- 代码质量下降，维护成本增加
- 性能问题明显，影响用户体验
- 新功能开发困难，扩展性差
- 技术债务积累，影响开发效率

### Q: 重构过程中如何保证功能正确性？
A: 保证功能正确性的方法：
- 建立完善的测试体系
- 采用渐进式重构策略
- 进行充分的回归测试
- 建立快速回滚机制

### Q: 如何评估重构的效果？
A: 重构效果评估指标：
- 代码质量指标（复杂度、重复度等）
- 性能指标（响应时间、吞吐量等）
- 开发效率指标（开发速度、bug率等）
- 维护成本指标（维护时间、修改难度等）
