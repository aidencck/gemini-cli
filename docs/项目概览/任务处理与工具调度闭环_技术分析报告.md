# 任务处理与工具调度闭环_技术分析报告

面向技术专家与架构师，系统化、结构化梳理当前工程中“任务（Tool Call）如何被识别、调度、执行、回传并闭环”的完整处理链路，覆盖核心模块、数据契约、事件流转、状态机、CLI 与 Core 的协作以及容错与取消机制。

---

## 一、总体视图与目标
- 目标：清晰定义“从用户输入到 LLM 产出工具调用，再到工具执行，结果回传给模型，最终生成用户可见回复”的闭环流程。
- 范畴：CLI 展示/交互层、Core 工具调度层、Tool 注册发现层、Chat/Client 流式通信层、错误与取消的侧路处理。
- 关键特性：
  - 流式请求/响应管理（`sendMessageStream`）
  - 工具调用状态机（`validating → scheduled → executing → awaiting_approval → success/error/cancelled`）
  - 工具结果到模型的标准化回传（`FunctionResponse Part`）
  - CLI 层对历史与状态的可视化编排
  - 接近 Token 上限的历史压缩提示与决策

---

## 二、核心组件与职责分层
- CLI 展示/交互层（packages/cli）
  - `useGeminiStream.ts`：流式消息管理与工具调度桥接；当批次工具全部完成时立即提交 `FunctionResponse` 给模型。
  - `useReactToolScheduler.ts`：在 React 场景下对工具调度的可视化/状态管理包装，提供 `schedule` 与 `markToolsAsSubmitted`。
  - `slashCommandProcessor.ts`：斜杠命令解析；工具列表展示、MCP 配置反馈等。
  - `ToolMessage` 组件与相关测试：工具执行过程与结果的 UI 呈现与状态指示。
- Core 工具调度层（packages/core）
  - `coreToolScheduler.ts`（`CoreToolScheduler`）：统一的工具调用状态机与执行器；完成工具结果转化为 `FunctionResponse`，并对外抛出更新事件。
  - `nonInteractiveToolExecutor.ts`：非交互工具的直接执行路径（无需确认场景）。
  - `prompts.ts`：业务提示语与序列图注释，描述 Agent-Tool-MCP 的交互流程与期望。
- Tool 注册与发现层（packages/core/src/tools）
  - `tool-registry.ts`（`ToolRegistry`）：静态注册与 MCP 动态发现的统一入口；面向模型暴露可用工具集合。
- Chat/Client 通信层（packages/core/src/core）
  - `geminiChat.ts`：`sendMessage`/`sendMessageStream` 的流式管线、消息校验、历史维护、工具事件透传与结果处理示意。
  - `client.ts`：模型能力判断与历史压缩（`tryCompressChat`），在接近输入 Token 上限时触发压缩或告警事件。
- 工具结果规范化与日志
  - `convertToFunctionResponse`（在 `coreToolScheduler.ts` 内部使用）：统一将工具输出转为 Gemini `FunctionResponse` Part。
  - `mcp-tool.ts` 的 `processFunctionResponse`：对 MCP 工具响应进行文本与结构化结果的友好格式化（显示用途）。
  - `generateContentResponseUtilities.ts`：从 `GenerateContentResponse` 和 `Part` 抽取文本、函数调用与结构化数据的工具集。

## 三、任务处理闭环——端到端时序

### 1. 用户输入与流式发送（CLI → Chat）
- 用户在 CLI 输入文本或斜杠命令，`useGeminiStream.ts` 负责：
  - 记录输入为历史项，设定 `userMessageTimestamp`，计算 `StreamingState`。
  - 通过 `geminiClient.sendMessageStream(...)` 发起流式请求：
    - 初始化流 → 逐步接收 `Part` 与事件（包括工具调用候选）。
    - 若模型产出工具调用（函数调用），由 CLI 层桥接到工具调度层。

### 2. 工具调度初始化（Chat → CoreToolScheduler）
- `CoreToolScheduler.scheduleToolCalls(...)` 接收批次工具调用请求（`ToolCallRequestInfo[]`）。
- 对每个 `callId`：
  - 状态置为 `validating`，结合 `ToolRegistry` 与 `ApprovalMode` 决定是否需要用户确认。
  - 确认通过或无需确认后状态转为 `scheduled`，准备执行。

### 3. 工具执行（CoreToolScheduler → Tool）
- 状态转为 `executing`，调度执行：
  - 对可修改工具尝试 `modifyWithEditor`（比如在编辑器中预览或修订执行参数）。
  - 调用工具实现（本地工具或 MCP 工具），收集 `ToolResult`：
    - `ToolResult.llmContent`：供模型消费的结构化结果（例如 JSON、文本或混合 `PartListUnion`）。
    - `ToolResult.returnDisplay`：用于 CLI 呈现的可读结果。
  - 执行过程中通过 `outputUpdateHandler` 推送 `liveOutput`（CLI 实时展示）。
  - 执行结束：
    - 成功：构造 `FunctionResponse Part`（`convertToFunctionResponse(toolName, callId, llmContent)`），状态置为 `success`。
    - 失败：构造错误响应，状态置为 `error`。
    - 用户取消：捕获 `AbortSignal`，状态置为 `cancelled`。

### 4. 结果回传给模型（Core → CLI → Chat）
- 在 `useReactToolScheduler.ts` 中注册的回调 `onComplete` 会在“该批次所有工具均完成”后触发：
  - CLI 将批次工具最终状态写入历史用于展示（`mapTrackedToolCallsToDisplay`）。
  - 调用 `handleCompletedTools(...)` → 组装所有 `FunctionResponse Part` 并立即通过 `geminiClient.sendMessageStream(...)` 提交给模型。
  - 调用 `markToolsAsSubmitted(callIds[])` 标记为“已提交”，避免重复回传。
- 模型继续基于工具结果生成新的 `Part`：
  - 可能继续产生新的工具调用（闭环继续）或输出最终的可见文本。
  - CLI 根据 `StreamingState` 与 `pendingHistoryItem` 决定何时落地历史、何时提示等待确认等。

### 5. 闭环收敛与完成（Chat → CLI）
- 当模型不再产出工具调用且输出文本收束：
  - CLI 落地最终消息项，更新会话统计与 UI 状态。
  - 若本轮过程中接近 Token 上限，CLI 展示压缩提示（来自 `ServerGeminiChatCompressedEvent`）：
    - 文案示例：`IMPORTANT: This conversation approached the input token limit for ${config.getModel()}. ...`

## 四、关键状态机与事件
- 工具调用状态机（`CoreToolScheduler`）
  - `validating`：校验工具可用性、参数与是否需确认（`ApprovalMode`）。
  - `awaiting_approval`：等待用户确认（CLI 进入 `StreamingState.WaitingForConfirmation`）。
  - `scheduled`：排队待执行。
  - `executing`：执行中；支持 `liveOutput`。
  - `success`/`error`/`cancelled`：终止态；产出 `ToolCallResponseInfo`。
- CLI 流式状态（`useGeminiStream.ts`）
  - `Idle`、`Responding`、`WaitingForConfirmation`、`Canceling` 等，配合工具状态更新历史与 UI。
- 事件与回调
  - `onToolCallsUpdate`：执行过程中刷新工具状态以供 CLI 显示。
  - `onAllToolCallsComplete`：批次工具全部完成后触发，CLI 将其回传模型。
  - 错误事件：`ErrorEvent` 被格式化（`parseAndFormatApiError`）展示。
  - 压缩事件：`ServerGeminiChatCompressedEvent` 注入提示。

## 五、数据契约与类型约束
- 输入/输出 `Part` 与 `PartListUnion`（`@google/genai`）
  - 文本、函数调用、函数响应等类型；`FunctionResponse` Part 是工具返回模型的标准形式。
- 工具调用结构
  - `ToolCallRequestInfo`：`{ callId, name, args, isClientInitiated }`
  - `ToolCallResponseInfo`：`{ callId, responseParts, resultDisplay, error? }`
  - `TrackedToolCall`（CLI 展示用）：包含 `status`、`responseSubmittedToGemini`、`confirmationDetails` 等。
- 工具结果结构（`ToolResult`）
  - `llmContent`：用于构造 `FunctionResponse Part` 的模型输入内容。
  - `returnDisplay`：CLI 显示用文本/Markdown。
- 工具注册与发现（`ToolRegistry`）
  - `getAllTools()`、`getTool(name)`、按 MCP Server 过滤等；结合 `discoverMcpTools` 完成动态接入。

## 六、历史与压缩策略（闭环支撑）
- `client.ts` 的 `tryCompressChat`：
  - 结合模型能力与上下文大小计算是否需要压缩历史。
  - 接近上限时发出压缩事件；必要时对历史进行截断/归纳。
- `geminiChat.ts`：
  - 维护 `recordHistory` 的策略，将用户可见内容与工具组活动正确落地历史。
  - 思考（COT）类内容保持隔离（另见前置报告），避免污染上下文计数与展示。

---

## 七、错误、取消与确认侧路
- 错误处理：
  - 工具执行异常 → `error` 终止态，`ToolMessage` 在 CLI 用错误样式呈现。
  - API 失败 → 生成错误历史项，用户可见。
- 取消处理：
  - 用户触发取消 → 调度器捕获 `AbortSignal`，置 `cancelled`，CLI 追加提示 `User cancelled the request.`。
- 确认处理（`ApprovalMode`）：
  - 需要确认的工具调用 → 进入 `awaiting_approval`，CLI 流状态调整并提示用户。

## 九、改进建议（工程实践）
- 统一确认策略：在 `ApprovalMode` 下细粒度配置（按工具、按风险级别）以减少阻塞。
- Tool 输出校验：对 `llmContent` 加强 JSON Schema 校验与错误恢复策略，提升回传的稳定性。
- LiveOutput 标准化：定义跨工具的标准流式输出接口，便于统一 UI 呈现与日志采集。
- 历史压缩策略：引入“语义摘要 + 最近 K 轮原文”混合策略，提高压缩效果同时保留最新上下文的高保真。
- 端到端遥测：在 `logToolCall` 与 CLI 入口增加时序与性能指标，便于定位瓶颈。

## 十一、总结（闭环心智模型）
- 入口：用户输入经 CLI 发起 `sendMessageStream`。
- 识别：模型在流中产出函数调用 → CLI 转交调度器。
- 执行：调度器依据状态机执行工具，收集结果并构造 `FunctionResponse`。
- 回传：CLI 在批次完成后将所有 `FunctionResponse` 统一回传模型，避免重复。
- 收敛：模型据此生成文本或继续工具调用，直到无工具调用 → CLI 落地最终历史项。
- 支撑：历史压缩与错误/取消/确认机制，保障闭环在复杂场景下仍然稳定与可控。
