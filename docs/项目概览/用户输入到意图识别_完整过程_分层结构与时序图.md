# 项目从用户输入到意图识别的完整过程

面向高级技术专家的体系化、系统化、结构化、分层次技术说明，覆盖从 CLI 入口到模型判定与工具调用的全链路，并提供可复用的时序图与代码映射索引。

## 目标与范围
- 明确“从用户输入到意图识别”的端到端路径、参与组件与数据契约。
- 梳理非交互模式（Headless CLI）与交互模式（Ink UI）共性流程，重点落在非交互模式实现。
- 给出时序图、状态与质量门控，标注核心控制点与扩展点。

## 总览与关键参与者
- 入口层：`packages/cli/src/gemini.tsx`（主入口）、TTY 判定、沙箱与认证、配置加载。
- 会话层：`GeminiClient.getChat()` + `GeminiChat`（消息/历史/流式处理/重试/回退）。
- 模型与提示层：`packages/core/src/core/prompts.ts`（系统提示与工具使用策略）。
- 工具编排层：`ToolRegistry` 注册/发现/声明；`executeToolCall` 执行；`coreToolScheduler` 响应封装。
- 工具执行层：`GrepTool`、`GlobTool`、`ReadFileTool`、`EditTool`、`WriteFileTool`、`ShellTool`、`WebSearchTool`、`MemoryTool` 等。
- 支撑层：`config`（模型/审批/沙箱/文件服务）、`telemetry`（请求/响应/错误）、错误处理与回退。

## 分层架构与代码映射
### 1) 入口层（CLI/沙箱/配置/认证/TTY 判定）
- 文件：`packages/cli/src/gemini.tsx`
  - 加载 `settings`、`extensions`，构造 `config`；根据内存与沙箱策略重启/进入沙箱。
  - TTY 判定：`stdin.isTTY && input.length === 0` -> 渲染 Ink UI；否则走非交互模式。
  - 认证：在进入沙箱前执行 OAuth 验证，避免重定向被沙箱拦截。
  - 日志：`logUserPrompt(config, {...})` 上报用户输入事件。
  - 非交互：`runNonInteractive(nonInteractiveConfig, input)` 进入头模式主循环。

### 2) 非交互主循环（消息/工具/闭环）
- 文件：`packages/cli/src/nonInteractiveCli.ts`
  - 初始化：`geminiClient = config.getGeminiClient()`；`toolRegistry = await config.getToolRegistry()`；`chat = await geminiClient.getChat()`。
  - 输入封装：`currentMessages = [{ role: 'user', parts: [{ text: input }] }]`。
  - 流式调用：`chat.sendMessageStream({ message: parts, config: { abortSignal, tools: [{ functionDeclarations: toolRegistry.getFunctionDeclarations() }] } })`。
  - 边收边写：过滤 `thought`，将 `text` 直接写到 `stdout`；收集 `functionCalls`。
  - 有函数调用：迭代 `functionCalls` -> 构造 `ToolCallRequestInfo` -> `executeToolCall(...)` -> 收集 `responseParts`（文本或结构化 `Part`）-> 将这些 `parts` 作为“下一轮用户消息”回灌模型。
  - 无函数调用：流结束，输出换行并返回。

### 3) 会话层（GeminiChat：历史/重试/流式/回退/遥测）
- 文件：`packages/core/src/core/geminiChat.ts`
  - 历史：`getHistory(true)` 生成“精简历史” + 当前用户内容；`recordHistory(user, modelOutput, afcHistory)` 写入模型输出与 AFC（自动函数调用）历史。
  - 非流式：`sendMessage(...)` 内部调用 `contentGenerator.generateContent(...)`，带指数退避重试与 429/5xx 策略，支持“模型回退”。
  - 流式：`sendMessageStream(...)` 调用 `contentGenerator.generateContentStream(...)`，并在 `processStreamResponse(...)` 中进行遥测、历史与响应合并。
  - 遥测：`_logApiRequest/_logApiResponse/_logApiError` 记录请求/响应/错误并附带使用指标。
  - 状态：内部 `sendPromise` 保证消息串行；维护 `history`、`usageMetadata` 与 AFC 历史裁剪。

### 4) 模型与提示层（系统提示与工具路由）
- 文件：`packages/core/src/core/prompts.ts`
  - 提供问题求解与应用开发工作流的系统提示：Understand → Plan → Implement → Verify。
  - 强化工具使用：优先用 `GrepTool/GlobTool/ReadFileTool/EditTool/WriteFileTool/ShellTool`；强调绝对路径与非交互命令、并行与流式返回。
  - MCP 交互分析：描述 LLM Agent、Tool Registry、MCP Client/Server 的时序与控制。
  - 意图识别本质：模型通过“结构化函数调用（FunctionCall）”显式表达意图（选择工具 + 参数），由工具层执行并将结果回灌继续对话。

### 5) 工具编排层（注册/执行/封装）
- 文件：`packages/core/src/config/config.ts`
  - `getToolRegistry()` 注册核心工具：`LSTool/ReadFile/Grep/Glob/Edit/WriteFile/WebFetch/ReadManyFiles/Shell/Memory/WebSearch`。
- 文件：`packages/core/src/core/coreToolScheduler.test.ts`
  - 校验 `CoreToolScheduler` 的调用与 `convertToFunctionResponse` 的封装格式（结构化 `Part`）。
- 文件：`ToolRegistry` 与 `executeToolCall`（路径在 core 导出集中）
  - `ToolRegistry.getFunctionDeclarations()` 提供函数声明给模型做工具发现。
  - `executeToolCall(config, requestInfo, toolRegistry, abortSignal)` 执行工具、处理错误并返回 `responseParts`（文本或 `Part`）。

### 6) 工具执行层（本地/网络/内存/系统）
- 本地检索：`GrepTool` 通过正则/`ripgrep` 实现文件扫描；不使用 LLM 进行检索，仅模型用于工具选择与结果解释。
- 文件/编辑：`ReadFileTool/EditTool/WriteFileTool/ReadManyFilesTool` 提供读改写能力，受 `ApprovalMode` 控制。
- 系统命令：`ShellTool` 执行非交互命令（配合 YOLO 审批或受限模式）。
- 网络检索：`WebSearchTool` 通过网络与模型完成摘要与引用；与本地检索路径隔离。
- 内存：`MemoryTool` 提供对话内记忆与上下文注入能力。

### 7) 支撑层（认证/沙箱/审批/遥测/错误）
- 认证与沙箱：入口处在进入沙箱前完成认证；沙箱与内存参数可能触发进程重启。
- 审批模式：`ApprovalMode.YOLO` 允许写操作工具；非 YOLO 时只启用只读工具（`loadNonInteractiveConfig` 中过滤）。
- 遥测：统一采集请求/响应/错误/使用指标；EPIPE/取消等边界处理在 CLI 层。
- 错误与回退：指数退避、模型回退、分类日志、用户提示；工具未发现与执行错误分级处理。

## 数据契约与类型关键点
- 输入消息：`Content`/`Part`（`{ role: 'user', parts: [{ text }] }`）与 `thought` 过滤。
- 工具调用：`FunctionCall`（模型输出的函数调用）→ `ToolCallRequestInfo`（执行层契约）。
- 工具响应：`FunctionResponse` 封装为结构化 `Part`（文本/JSON/富结构），通过 `convertToFunctionResponse` 返回给模型。
- 历史：精简历史（curated history） + AFC 历史裁剪与合并，避免重复。

## 意图识别机制与判定策略
- 模型通过系统提示（`prompts.ts`）学习到工具使用规范与策略，利用函数调用表达意图（工具选择与参数）。
- 判定来源：函数调用即“意图识别的显式表达”。当存在函数调用时，进入“工具执行 + 结果回灌”闭环；当不含函数调用时，表示模型认为文本回答即可完成。
- 路由与约束：
  - 优先使用本地工具（`Grep/Read/Glob/Edit/Write/Shell`）进行检索与读写；强调绝对路径与非交互命令、并行与流式返回。
  - `ApprovalMode` 限制写操作工具在非 YOLO 模式未授权时不可用（在 `loadNonInteractiveConfig` 中过滤）。
  - `AbortSignal` 支持取消，错误分类与审计记录提供可恢复性。

## 本地检索与 LLM 使用界限（重要）
- 本地代码检索路径：`GrepTool` 等不使用 LLM 进行检索与内容生成；`llmContent` 字段仅用于格式化/说明文本。
- 网络检索路径：`WebSearchTool` 使用模型进行外部搜索摘要与引用，这是与本地检索独立的路径。
- 语义/向量/AST 检索：在当前代码库中未实现，保留为规划特性（参见已有文档《工程总搜索功能_全链路闭环流程_技术说明.md》中的建议）。

## 质量门控与指标（建议）
- 响应时间：TTFB < 2s；完整响应 < 10s；工具调用 < 5s。
- 可靠性：成功率 > 99%；重试率 < 5%；回退率 < 1%。
- 资源：内存 < 100MB；CPU < 50%；带宽自适应。
- 门禁：错误分级（环境/权限/解析/超时/取消）；非 YOLO 模式禁止写操作；大范围/长时任务需提示与确认。

## 边界、安全与审计
- 路径白名单与沙箱：限制工作区；防路径遍历；进入沙箱前完成认证。
- 数据脱敏：日志与预览中对敏感信息做最小披露与脱敏。
- 审计与留痕：记录输入、函数调用、工具响应、错误与度量，支持复盘。

## 未来演进与建议
- 明确默认搜索与检索模式为非 LLM，避免隐性成本与风险。
- 设计“混合检索服务”作为可插拔扩展（`hybridSearchService.ts`），支持：
  - 外部嵌入索引与向量库（`topK/minScore`）；
  - 符号/AST 通道与语义通道的合并、去重与排序；
  - 门控阈值与审批策略；
  - 与 `ToolRegistry` 的最小耦合集成（作为新工具或内部策略层）。
- 在 CLI 提供“LLM 介入控制”开关（关闭/半开/全开），并在 UI 暴露当前模式与风险提醒。
