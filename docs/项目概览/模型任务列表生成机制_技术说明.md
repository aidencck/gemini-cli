# 模型任务列表生成机制_技术说明

面向技术专家与架构师，系统化阐述模型如何依据《任务处理与工具调度闭环_技术分析报告》中的事件、状态与数据契约，生成“具体任务列表数据”。目标是给出可落地的数据模型、字段映射、分层构建流程与校验策略，并以示例与端到端案例说明。

---

## 1. 背景与目标
- 背景：在 CLI 流式交互中，模型产出函数调用（工具调用），由 Core 调度执行并回传结果，形成端到端闭环。我们需要将这套过程“结构化为任务列表数据”，用于可视化、编排与回溯。
- 目标：
  - 定义任务项（Task Item）的统一数据模型与分层组织方式。
  - 明确任务字段的来源（来自 CLI/Core/工具执行/事件）。
  - 给出从流事件到任务列表的构建算法与更新策略。
  - 提供示例 JSON 与端到端生成流程，便于工程落地与验证。

---

## 2. 概念与输入源
- 会话与批次：一次用户请求 → 模型可能产出“一批次”工具调用（batch）。
- 工具调用（Tool Call）：`ToolCallRequestInfo { callId, name, args, isClientInitiated }`
- 状态机（CoreToolScheduler）：`validating → awaiting_approval → scheduled → executing → success/error/cancelled`
- 关键事件：
  - `onToolCallsUpdate`（过程态刷新）
  - `onAllToolCallsComplete`（批次完成 → 回传 `FunctionResponse`）
  - CLI 流状态：`Responding / WaitingForConfirmation / Idle`
- 旁路：
  - Checkpoint：`saveRestorableToolCalls` 在 `awaiting_approval` 时创建文件快照与 JSON 记录。
  - Restore：`/restore` 选择 checkpoint → `gitService.restoreProjectFromSnapshot` → 重排工具调用。

---

## 3. 任务列表数据模型
面向前端展示与编排的“任务项”统一结构：

```json
{
  "taskId": "string",              // = callId
  "title": "string",               // 友好标题（基于 toolName + args 摘要）
  "toolName": "string",            // 工具名
  "status": "validating|awaiting_approval|scheduled|executing|success|error|cancelled",
  "priority": "low|medium|high",   // 基于风险、确认需求与上下文压力推断
  "batchId": "string",             // 批次标识（同一流内一次性产出的调用集）
  "sessionId": "string",           // 会话标识
  "isClientInitiated": true,
  "createdAt": "ISO8601",
  "updatedAt": "ISO8601",
  "dependsOn": ["taskId"],         // 任务级依赖（如结果前后关联）
  "argsPreview": "string",         // 参数摘要用于 UI
  "confirmationRequired": true,
  "confirmationDetails": {
    "reason": "string",
    "state": "pending|approved|rejected"
  },
  "liveOutputRef": "string",        // 流式输出引用（展示用）
  "resultDisplay": "string",        // CLI 展示文本/Markdown
  "functionResponseRef": "string",  // 结构化 FunctionResponse 存储引用
  "errorMessage": "string|null",
  "responseSubmittedToGemini": true,
  "tokenPressure": "normal|warning|critical", // 源于压缩事件
  "checkpoint": {
    "commitHash": "string",
    "filePath": "string"
  },
  "restoreAvailable": true,
  "tags": ["string"]
}
```

分层组织：
- 会话层（Session）：`sessionId` → 管理所有批次与任务项。
- 批次层（Batch）：`batchId` → 管理同轮工具集合与聚合状态。
- 任务层（Task Item）：细粒度状态、输出与引用信息。

---

## 4. 字段映射与来源
- `taskId`：`ToolCallRequestInfo.callId`
- `title`：`toolName + args` 生成的可读摘要（防泄露敏感字段）
- `toolName`：`ToolCallRequestInfo.name`
- `status`：来自 `TrackedToolCall.status`（CLI）或调度器状态事件
- `priority`：
  - 高：需要确认（`awaiting_approval`）、风险型工具（文件写入/替换）、高 token 压力
  - 中：执行中或计划执行（`scheduled|executing`）
  - 低：成功/取消/轻量查询类工具
- `batchId`：在一次 `sendMessageStream` 响应周期内的调用组标识
- `sessionId`：当前会话标识（CLI 维护）
- `isClientInitiated`：来自 `ToolCallRequestInfo.isClientInitiated`
- `createdAt`：流接收首个事件时间或 `userMessageTimestamp`
- `updatedAt`：最近状态更新事件时间
- `dependsOn`：同批次内根据工具调用的语义与引用关系推断（例如某调用需要前一调用结果）
- `argsPreview`：从 `args` 生成的摘要（截断/脱敏）
- `confirmationRequired` / `confirmationDetails`：`awaiting_approval` 触发；理由来自工具类别与策略（ApprovalMode）
- `liveOutputRef`：过程态输出引用（CLI 管理）
- `resultDisplay`：`ToolResult.returnDisplay`
- `functionResponseRef`：`convertToFunctionResponse(...)` 的结果存储引用
- `errorMessage`：`parseAndFormatApiError` 或工具异常信息
- `responseSubmittedToGemini`：`markToolsAsSubmitted(callIds)` 之后置为 true
- `tokenPressure`：`ServerGeminiChatCompressedEvent` 映射为 `normal|warning|critical`
- `checkpoint.commitHash/filePath`：来自 `saveRestorableToolCalls`（`gitService.createFileSnapshot` + JSON）
- `restoreAvailable`：当存在 checkpoint 信息时为 true
- `tags`：基于工具类别（读/写/网络/文件系统/MCP）与风险级别自动附加

## 5. 构建流程与算法说明
给出从流事件到任务列表的生成与更新算法（伪代码）：

```ts
function buildTasksFromStream(events, sessionId) {
  const batches = groupByBatch(events);
  const tasks = [];

  for (const batch of batches) {
    const batchId = batch.id;
    for (const call of batch.toolCalls) {
      const task = createInitialTask(call, { batchId, sessionId });
      tasks.push(task);
    }

    for (const e of batch.events) {
      switch (e.type) {
        case 'ToolCallsUpdate':
          applyStatusUpdates(tasks, e.updates);
          break;
        case 'AllToolCallsComplete':
          attachFunctionResponses(tasks, e.functionResponses);
          markSubmitted(tasks, e.callIds);
          break;
        case 'CheckpointCreated':
          attachCheckpoint(tasks, e.callId, e.commitHash, e.filePath);
          break;
        case 'CompressionWarning':
          tagTokenPressure(tasks, batchId, e.level);
          break;
        case 'Error':
          recordError(tasks, e.callId, e.message);
          break;
      }
    }
  }
  return normalize(tasks);
}
```

关键策略：
- 初始任务：`status=validating`，`priority` 基于工具类型与确认需求预估。
- 状态更新：以 `TrackedToolCall.status` 为权威；每次事件更新 `updatedAt`。
- 提交标记：在批次完成并成功回传 `FunctionResponse` 后，设置 `responseSubmittedToGemini=true`。
- 依赖分析：同批次工具的语义引用（如第二个工具读取第一个工具产物）形成 `dependsOn`。
- Checkpoint：在 `awaiting_approval` 时记录 `checkpoint` 字段，提升可恢复性与风险控制。

## 6. 分层组织与聚合
- 会话层聚合：
  - 指标：批次数量、成功率、平均确认等待时长、错误率、压缩警告次数。
- 批次层聚合：
  - 状态：`all_success|partial_error|awaiting_approval|mixed`（基于任务集合态）
  - 行为：在 `onAllToolCallsComplete` 后聚合展示与回传模型。
- 任务层：
  - 明细：状态、输出、错误、确认与恢复能力。

## 8. 端到端案例（从输入到任务）
1) 用户输入 → `sendMessageStream` 启动；模型产出两条函数调用。
2) 构建初始任务（`validating`），填充 `sessionId/batchId` 与 `argsPreview`。
3) `awaiting_approval` 触发 → 高优先级、生成 `checkpoint` 字段。
4) 执行完成 → 附加 `resultDisplay` 与 `functionResponseRef`，成功项置 `responseSubmittedToGemini=true`。
5) 若出现压缩事件 → 批次任务 `tokenPressure=warning/critical`。
6) `/restore` 执行 → 依据 `checkpoint.commitHash` 回滚并重排 `taskId` 对应调用。

---

## 9. 异常与边界处理
- 工具异常：填充 `errorMessage` 与 `status=error`，保持其在聚合中可见。
- 用户取消：`status=cancelled`，保留 `liveOutputRef` 以便审计。
- 确认拒绝：`confirmationDetails.state=rejected` → 任务终止且不回传模型。
- 多批次交错：通过 `batchId` 保持隔离，避免状态串扰。

---

## 10. 校验与度量
- 完整性：`taskId/toolName/status` 必填，`batchId/sessionId` 一致性校验。
- 终止一致性：批次完成后，所有成功项必须 `responseSubmittedToGemini=true`。
- 风险标注：存在写入/替换类工具且未 checkpoint → 发出告警。
- 性能指标：生成耗时、事件处理时延、错误率与确认等待时长。

---

## 11. 存储与命名建议
- 存储位置：
  - 临时任务快照可写入项目临时目录（`getProjectTempDir()`）下的 `tasks/` 子目录。
  - 与 checkpoint JSON 对齐，便于 `/restore` 场景联动。
- 命名规范：`<session>-<batch>-<call>-<tool>-<ts>.json`

---

## 12. 总结
通过统一的数据模型、清晰的字段来源与可复用的构建算法，模型能够将“工具调用闭环中的动态事件”稳定地映射为“具体任务列表数据”。该任务列表既服务于前端展示与交互，也承载审计、恢复与自动化编排的基础。
