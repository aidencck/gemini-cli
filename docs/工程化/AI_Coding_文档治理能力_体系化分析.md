# AI Coding 文档治理能力：体系化、系统化、结构化分析

## 文档目的
- 建立面向 AI Coding 的“文档治理能力”框架，支撑可持续的知识生产、复用与合规。
- 以分层模型抽象治理原则、流程方法、能力模块与技术支撑，指导落地与度量升级。

## 范围与对象
- 范围：项目内所有知识资产（需求/架构/实现/运维/测试/RAG语料/Prompt/COT 等）。
- 对象：工程团队、文档运营、平台/数据团队、合规与安全团队。

---

## 分层模型（价值 → 策略 → 流程 → 能力 → 技术）

### 1) 业务价值层
- 用户价值：降低认知与检索成本，缩短学习与协作周期。
- 管理价值：形成可追踪、可度量、可审计的知识治理闭环。
- 合规价值：隐私最小化、访问控制与留痕，满足审计要求。
- 生态价值：统一模板与接口，促进跨团队复用与持续演进。

### 2) 治理策略层（原则）
- 统一：统一模板、命名与目录组织，减少碎片化与差异化。
- 可追踪：版本化、评审留痕与发布记录，确保可回溯性。
- 结构化：元数据前置、分层内容结构，支持语义检索和 RAG。
- 自动化：CI 校验、门禁策略与脚本化操作，降低人为偏差。
- 可观测：度量指标与报表，驱动持续改进与决策支持。
- 最小敏感：隐私/密钥信息最小暴露与脱敏，合规优先。

### 3) 业务流程层（端到端闭环）
1. 文档采集：汇聚多源内容（代码库、会议纪要、工单、聊天记录）。
2. 结构化处理：清洗、分段、抽取关键元数据（主题、版本、角色、关联）。
3. 编目与标签：建立规范化目录、命名与标签体系（可多维检索）。
4. 审校与评审：内容校对、技术评审与合规审核（留痕与责任人）。
5. 版本管理与发布：PR 合并、版本标注与发布说明（Changelog）。
6. 分发与检索：索引生成、主题渲染与多渠道分发（README/索引页）。
7. 更新与变更治理：触发条件（代码变更/依赖升级）、更新任务与 SLA。
8. 归档与退役：过期识别、兼容性说明与退役策略（保留访问路径）。

### 4) 业务能力层（能力组件）
- 模板与标准：统一 Markdown 模板、Front Matter 元数据。
- 元数据模型：标题、作者、责任人、状态、版本、适用范围、关联文档、标签。
- 目录与命名：按领域/层级组织（例如：`docs/项目概览`、`docs/工程化`）。
- 质量门禁：链接有效性、重复检测、元数据完整性、风格一致性。
- 角色与 RACI：Owner/Reviewer/Maintainer/Approver 明确分工与 SLA。
- 知识关联：需求→设计→实现→测试→运维→RAG 语料→Prompt/COT 映射。
- 摘要与索引：自动生成摘要、目录与跨文档索引，便于“入口统一”。
- 语义检索与 RAG：嵌入向量、召回与生成增强，支持智能问答与总结。
- 自动化流：脚本化工具与 CI 集成，形成可执行的治理流水线。

### 5) 技术支撑层（项目内映射）
- 代码仓库/Git：版本与评审留痕（PR/Commit），`CODEOWNERS` 指定责任人。
- CI/CD：`.github/workflows/ci.yml`、`e2e.yml` 执行检查与集成测试。
- 脚本工具：`scripts/doc-manager.sh`、`scripts/git/quick-doc-branch.sh`、`scripts/git/quick-submit.sh`。
- 文档体系：`docs/项目概览/*`、`docs/工程化/*`、`docs/架构/*`、`docs/tools/*`、`docs/model/*`。
- 规范文件：`CONTRIBUTING.md`、`README.md`、`docs/项目概览/README.md`（可作为索引入口）。
- 主题与渲染：`docs/cli/themes.md` 与 `docs/assets/*` 提升可读性与一致性。
- 遥测与统计：`scripts/local_telemetry.js`、`telemetry*.js`（可扩展文档访问与更新统计）。

## 指标与度量（建议 SLO）
- Freshness（新鲜度）：近 90 天更新占比 ≥ 70%，过期标注覆盖率 ≥ 95%。
- Coverage（覆盖度）：核心域文档齐备率 ≥ 95%（需求/设计/实现/测试/运维）。
- Consistency（一致性）：元数据完整率 ≥ 98%，命名/目录规范通过率 ≥ 98%。
- Accuracy（准确性）：评审缺陷率 ≤ 2%，发布后纠错率 ≤ 5%。
- Discoverability（可发现性）：索引命中率 ≥ 90%，平均检索耗时 ≤ 5s。
- Reuse（复用度）：跨团队引用次数/季度增长 ≥ 20%。
- Review SLA：关键文档评审时长 ≤ 48h，紧急修订 ≤ 24h。

## 质量门禁设计（落地示例）
- Pre-Commit：
  - Front Matter 校验（必填元数据：`title`、`owner`、`status`、`version`、`tags`）。
  - 命名与目录规范检查（禁止空文件与随机命名）。
- CI 阶段：
  - 链接有效性与锚点检查；重复内容检测（相似度阈值）。
  - 索引更新校验：新增文档必须在 `docs/项目概览/README.md` 或对应目录索引登记。
  - 术语表/词汇统一检查（避免同义词混用）。
- 发布阶段：
  - 生成 Changelog 与影响范围；标注替代/退役路径与相容性说明。

## 风险与对策
- 碎片化与重复：建立统一索引与重复检测，聚合相似文档并合并。
- 过期与漂移：新鲜度告警与退役流程，代码变更触发文档更新任务。
- 孤儿文档：无入口/无引用的文档自动标记并纳入整改清单。
- 隐私泄露：密钥/私有数据扫描与脱敏，最小权限访问控制。
- 风格不一致：模板与风格检查，主题统一与术语表治理。
- 审校缺位：RACI 明确责任，`CODEOWNERS` 强制评审与 SLA。

## 路线图（示例）
- M1（2–4 周）：统一模板与 Front Matter、索引入口、CI 门禁基础版。
- M2（4–8 周）：重复检测/链接检查、术语表治理、RACI 与 `CODEOWNERS` 完成。
- M3（8–12 周）：语义检索/RAG 接入、遥测报表与治理仪表板，SLO 驱动改进。

---

## 操作清单（实践指南）
- 新增文档：使用统一模板，填写 Front Matter 与标签，并更新索引。
- 修改文档：更新版本与变更原因，评审通过后发布，并记录影响范围。
- 退役文档：标注替代方案与兼容性说明，保留访问路径与历史链接。
- 周期治理：每月重复/孤儿/过期扫描，发布改进事项与责任人。
